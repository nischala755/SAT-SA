# SAT-SA Phase 1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking.

**Goal:** Establish a runnable offline foundation with typed contracts, local persistence, deterministic synthetic evidence and a connected application shell.

**Architecture:** Next.js/TypeScript web application calls FastAPI/Pydantic through a same-origin server route. Python repository interfaces isolate DuckDB metadata/audit storage and immutable Parquet datasets. One API process owns serialized writes; no analytics jobs or signal calculations are implemented in this phase.

**Tech Stack:** Next.js, React, TypeScript, FastAPI, Pydantic, DuckDB, PyArrow for explicitly typed Parquet writing, Pytest, Vitest, Docker Compose. PyArrow is justified by deterministic columnar serialization and explicit schemas, not a second query engine.

**Spec:** `docs/architecture.md`, the supplied SAT-SA problem statement, and the user's Phase 1 requirements.

## Global constraints

- The supplied SAT-SA problem statement is the authoritative source for functional requirements.
- `architecture.md` is the authoritative source for system architecture and implementation boundaries.
- `AGENTS.md` is the authoritative source for engineering behaviour, coding standards, testing discipline, and agent constraints.
- Do NOT implement the full analytics engine, review prioritization, dashboards, or polished UI in Phase 1.
- Do NOT create mock analytical results or hard-code findings into the application.
- The application must be runnable at the end of Phase 1.
- No external runtime requests, remote fonts, CDN assets, telemetry, cloud services or external AI dependencies.
- Stop after the Phase 1 verification report. Do not proceed to Phase 2.
- Existing AGENTS.md is empty. Preserve it rather than inventing user-approved constraints.

## Review focus

1. Naive timestamps and reversed lifecycle timestamps must fail validation; missing evidence remains representable.
2. Identical seeds must reproduce logical records and file hashes without wall-clock timestamps leaking into generated artifacts.
3. Reopening persistence must retain dataset registrations and audit entries; duplicate versions must not overwrite immutable data.
4. Entity-local identifiers must not create cross-entity alert/case/event links.
5. A unavailable API or storage initialization failure must be visibly reported, not shown as healthy.
